# 10. 배포 전략 + 향후 확장성 (100만 유저 기준)

## 1. 배포 전략

### 클라이언트 CI/CD
- GitHub Actions (or Codemagic): PR → lint/test → `flutter build` (Android AAB / iOS IPA)
- Flavor 분리: `dev` / `staging` / `prod` (다른 API base URL, 앱 아이콘/이름으로 구분)
- 코드사이닝: Android는 Play App Signing, iOS는 Fastlane match로 인증서 관리
- 스토어 배포: 내부테스트 → 비공개 베타(Google Play 비공개 트랙 / TestFlight) → 단계적 공개 출시(5%→20%→100% 롤아웃)
- 원격 설정(Firebase Remote Config 등)으로 기능 플래그 제어 — 신규 기능(AI챗 등)을 서버 배포 없이 점진 노출

### 서버 CI/CD
- 컨테이너화(Docker) + 오케스트레이션(단일 리전 시작 시 관리형 컨테이너 서비스로 충분, 이후 Kubernetes 전환 검토)
- 배치 수집 파이프라인은 별도 워커 프로세스/큐(예: 메시지 큐 + 스케줄러)로 API 서버와 분리 배포 — 정부 API 장애가 사용자 트래픽에 영향 주지 않도록 격리
- Blue-Green 또는 Rolling 배포로 무중단 배포

## 2. 확장성 아키텍처 (100만 유저 목표)

```
[클라이언트]
    │
    ▼
[CDN / API Gateway]  ── 정적/캐시 가능한 응답(혜택 목록 등) 엣지 캐시
    │
    ▼
[API 서버 (Stateless, 오토스케일)]
    │        │
    ▼        ▼
[Redis 캐시]  [PostgreSQL (Read Replica)]
    │
    ▼
[배치 수집 워커] ── [정부 Open API들]
    │
    ▼
[AI 서비스 레이어] ── [LLM Provider(교체 가능)]
```

- **API 서버는 Stateless**로 설계해 수평 확장(오토스케일) — 세션 상태는 Redis/JWT로 외부화.
- **읽기 트래픽 분리**: 혜택 목록/상세 조회는 압도적 다수의 읽기 트래픽 → Read Replica + Redis 캐시로 DB 부하 흡수.
- **룰 평가 캐시**: 동일 프로필 해시에 대한 평가 결과를 캐시해 룰엔진 재계산 비용 절감 ([09 참고](09-testing-security-performance.md)).
- **AI 레이어 분리**: LLM 호출은 지연시간이 크고 비용이 높으므로 별도 서비스로 분리, 큐잉/동시성 제한을 두어 급증 트래픽에도 API 서버 자체는 영향받지 않게 격리.
- **데이터 수집 파이프라인은 워커 풀로 수평 확장**, 소스별 독립 큐로 한 소스의 장애가 다른 소스 수집을 막지 않도록 격리.

## 3. 데이터 볼륨 대비

- 정부 혜택 데이터는 수천~수만 건 수준으로 트래픽 대비 작음 → 정적 캐시 전략이 매우 효과적.
- 사용자 데이터(프로필, 북마크, 알림 로그)가 100만 유저 규모에서 커지므로 `notification`, `ai_message` 같은 append-only 로그성 테이블은 파티셔닝(월 단위) 및 오래된 데이터 아카이빙 정책 필요.

## 4. 지역 확장

- 17개 시/도 데이터 소스가 순차 추가될 것을 고려해 `benefit_source`/어댑터 구조가 이미 확장 가능하게 설계됨 ([04 참고](04-api-layer-integration.md)).
- 향후 다국어(외국인 근로자 대상 혜택 등) 확장 가능성을 염두에 두고 `benefit` 콘텐츠 필드는 지금부터 로케일 확장 여지를 남겨둔다 (MVP는 한국어 단일).

## 5. 장애 대응

- 정부 API 소스 하나가 장애가 나도 다른 소스 수집/서비스에는 영향 없음 (어댑터 격리).
- API 서버 장애 시에도 클라이언트는 로컬 캐시로 핵심 화면(홈/상세/북마크) 계속 제공 가능 — 오프라인 우선 설계의 실질적 이점.
